# Sudoku — C11 exact solver, CLI and quality gates (`v0.8.4`, experimental)

A fully offline Sudoku engine with deterministic exact solving, solution classification, validation and a scriptable CLI. The public solver API is input-preserving: passing the same `SudokuBoard` pointer as both puzzle and solution output now returns `SUDOKU_SOLVE_INVALID` without overwriting the puzzle; use a separate output board. POSIX resume now rejects non-regular paths such as FIFOs and character devices without blocking; POSIX game saves now stage through exclusive owner-only `mkstemp` paths rather than predictable timestamp/counter names; Windows game-save staging now uses an atomic Win32 counter and process ID alongside exclusive file creation; native Windows acceptance remains pending. v0.8.4 generation now fails closed if the CPU clock is unavailable or moves backwards, and rejects an expired generation deadline before returning success. **This is a development milestone, not a production release.** v0.7.0 added playable terminal Sudoku with notes, bounded undo/redo, check/reset, completion detection and checksummed atomic save/resume. The terminal now has **read-only full-board pencil visualizations**: `show notes` renders each cell's handwritten digits in a 3×3 mini-grid, while `show candidates` renders legal candidates computed from the current board (never the cached solution). Filled cells appear as `[digit]`; absent notes as `.`. Neither command edits the puzzle, timer, history, or save. `show` without arguments retains the existing 9×9 digit board. The interactive game now supports unit-scoped `notes fill row|column|box N` and `notes prune row|column|box N` (N=1..9). These update the editable empty cells in only one row, column, or 3×3 box as **one Undo action**, leaving all other cells and placed digits unchanged. Fill computes live Sudoku candidates; prune removes only illegal marks without adding any. Repeated unchanged commands preserve Redo. For finer control, the interactive game supports cell-scoped `notes fill ROW COL` (replace one cell's handwritten marks with currently legal Sudoku candidates) and `notes prune ROW COL` (remove illegal marks from only that cell, without adding any); both are single-step Undo changes, history-neutral on no-op, and never consult the stored solution. The interactive game also supports `notes add ROW COL DIGITS` and `notes remove ROW COL DIGITS`, letting players add or erase several handwritten candidates in a **single Undo step** without replacing other marks. Existing/absent digits are idempotent no-ops, and invalid digits or targets cannot change the board. The interactive game supports `notes set ROW COL DIGITS` (e.g. `notes set 1 3 1359`) to replace all handwritten pencil marks in one undoable operation; `notes set ROW COL -` and `notes clear ROW COL` remove that cell's marks. DIGITS must be distinct 1–9 characters, in any order; invalid inputs never mutate the game, and unchanged sets preserve Redo. The interactive game now supports read-only `candidates ROW COL` to list legal Sudoku digits for a cell without revealing the answer or affecting undo/redo. The `hint hidden-triples [N]` command previews hidden triples in rows, columns and boxes; `hint apply hidden-triples [N]` removes only matching extra handwritten marks in one undoable edit (N defaults to 5; accepted range 1–81). The `hint triples [N]` command previews actionable naked triples in rows, columns and boxes; `hint apply triples [N]` removes only corresponding handwritten pencil candidates as one undoable action (default N=5, valid range 1–81). The `hint swordfish [N]` command previews three-row/three-column Swordfish eliminations, and `hint apply swordfish [N]` removes matching handwritten notes as a single undoable action (default N=5, range 1–81). The `hint x-wing [N]` command previews actionable row/column X-Wing eliminations, and `hint apply x-wing [N]` removes only corresponding handwritten pencil marks in one undoable action (default N=5, range 1–81). Both inspect live Sudoku constraints rather than the cached solved grid; neither guesses or inserts solution digits. Use `auto-notes` to fill legal pencil candidates across the board in one undoable step; this action deliberately replaces any handwritten notes, and repeated unchanged calls do not create redundant history. Use `prune-notes` instead to remove only now-invalid handwritten candidate marks, preserving legal choices and the undo/redo history as one editable action. Candidate calculation is now a single validated row/column/box bitmask operation rather than nine separate full-board trial validations; this preserves behavior while reducing repeated checks for `candidates`, `hint`, `auto-notes`, and `prune-notes`. Bulk note operations also fail without changing notes or history if the public board is malformed; the optimized internal helper validates the board once per bulk operation. It also offers a read-only `hint` command for the first forced naked/hidden single and `hint all` to list every distinct immediately forced cell without duplicate unit reports or state changes, or `hint apply all` to commit all those deductions in **one undoable batch**. New `hint chain [N]` previews up to N successive forced single-candidate/hidden-single steps opened by earlier moves without changing the game; `hint apply chain [N]` commits up to N steps in one undoable batch. N is an optional decimal count from 1 through 81 (default 81); the chain stops sooner if no further logical single exists (never guessing), using live Sudoku constraints (no stored-solution lookup). Explicit `hint apply` places just one deduction through the standard undoable move system. Both preview and application are blocked while incorrect player entries remain. Use read-only `check details` to locate the incorrect entries without revealing their correct solution digits, or explicitly run `check clear` to erase **only incorrect player-entered values** as one undoable action; no correct answers are inserted and existing pencil notes elsewhere are retained. v0.8.0 added development packaging; v0.8.4 makes interactive save paths with spaces usable and retains the selected path after a post-rename durability warning; v0.8.3 added POSIX save-directory metadata syncing and Linux fault-injection regression tests; v0.8.2 hardens the input-stream lifecycle and makes the Clang static analyzer part of the full local quality gate. Native Windows/macOS validation, license approval and an official release remain pending. The manual CI workflow now fails if its actual OS/CPU architecture does not match the requested native platform. The quality gate additionally requires the complete CTest test inventory (23 Linux and Windows / 22 macOS native Release checks, 20 instrumented checks on Linux/macOS) before testing, so missing, disabled or skippable Python-dependent E2E tests cannot masquerade as a passing run.

## Build and use

**Native package gameplay acceptance (v0.8.4):** The required `sudoku_package_e2e` CTest now runs the **extracted distribution executable** and the executable rebuilt from its **shipped source archive** through `play`: create a real save in a filename containing spaces, resume and verify a saved pencil note, reject a corrupted save with exit code 3, and confirm quitting never creates an implicit save. This makes the packaged save/resume path part of the exact-host quality gate instead of testing only `--version`/solve. An unsigned platform receipt now includes the mandatory `packaged_game_save_resume` check identifier, and the offline receipt matrix refuses receipts without it. None of this replaces native Windows/macOS evidence, owner licensing or signed release provenance.

**Source identity for acceptance receipts:** The native platform receipt and full cross-platform receipt-matrix verifier now derive their source-content digests and compare ZIP/TAR contents using a private, bounded snapshot of the *same* archive bytes validated against the declared SHA-256. Changing an archive pathname between a preliminary hash and parsing cannot substitute another source tree as valid evidence. `SHA256SUMS` and the local receipt remain unsigned and cannot establish authentic provenance; native Windows/macOS acceptance and licensing are still pending.

The three v0.8.4 development verification stages—package verification, per-host acceptance receipt generation, and cross-host receipt-matrix comparison—now agree on canonical `SHA256SUMS` formatting. A checksum file with reordered entries, CRLF/CR endings or a missing final newline is not acceptable receipt evidence. The receipt metadata remains unsigned, and the required clean Windows/macOS runs have not been completed.

Development packages are restricted to the roadmap's native Linux x86_64, Windows x86_64 and macOS arm64 targets. The checksum manifest must contain exactly four SHA-256 records sorted by archive **filename**, ASCII text with LF line endings and a terminating newline. The packager refuses to label unsupported host/CPU combinations as supported releases. This is a format/portability gate, not proof that native Windows or macOS tests have passed.

Development package creation now writes and validates the **entire five-file set** (platform ZIP/TAR.GZ, source ZIP/TAR.GZ, SHA256SUMS) in a private staging directory before publication. It refuses to replace existing artifacts and rolls back its own newly linked files on publication errors. Re-running into the same output folder requires a fresh destination: prior verified files are never silently overwritten. This protects previous results during normal failures; it does **not** provide crash-atomic publication of all five files or release signing.

The v0.8.4 development package verifier now validates each original archive once into a bounded private snapshot, then computes its checksum and decodes ZIP/TAR from **the same stored bytes**. This eliminates archive-path replacement between hashing and parsing on supported systems. Temporary copies are cleaned up; the checksum list remains unsigned, and this is not a signed or approved production release.

Development package verification checks `SHA256SUMS` and each ZIP/TAR archive on the **opened regular-file descriptor** before reading, rather than trusting a path-only preflight. POSIX FIFO, device and final-component symlink substitutions are rejected without a blocking open, and archive hashing enforces size and concurrent-content-length limits. This is local integrity hardening, not cryptographic signing or release approval.

The development source packager now pins each parent directory while opening the source manifest, manifested source files, and staged installation files on supported POSIX hosts; swapping a parent path to a symlink cannot redirect package reads outside the relevant root. On Windows this descriptor-relative traversal is unavailable, and packaging relies on the existing path/symlink and opened-file checks pending native validation. This improves source package integrity but does not constitute a signed or approved release.

Development source packaging rejects non-regular source or manifest inputs on the opened file descriptor, rather than relying solely on a pathname check. Untrusted writerless FIFOs do not block the packaging process on POSIX; this is source-integrity hardening, not an artifact signature or production certification.

For POSIX hosts, puzzle `--file` input must be a regular file (a symlink to a regular file is permitted); FIFOs and devices are rejected without blocking. Use `--stdin` or `--file -` to stream solver input instead. This behavior has not yet been verified on native Windows/macOS release targets.

Requires CMake 3.16+, a C11 compiler and (optionally) Python 3 for golden CLI tests.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
./build/sudoku --help
./build/sudoku --version
./build/sudoku solve --file tests/fixtures/unique.txt --format json
./build/sudoku count --file tests/fixtures/unsolvable.txt --format compact
./build/sudoku solve --stdin --format compact < tests/fixtures/unique.txt
./build/sudoku solve --file tests/fixtures/unique.txt --format json --output solution.json
./build/sudoku generate --seed 42 --difficulty medium --symmetry rotational --format json
./build/sudoku play --file tests/fixtures/unique.txt
./build/sudoku play --seed 42 --difficulty easy --save my-game.save
./build/sudoku play --resume my-game.save
```

On Windows with a multi-config generator, use `build/Release/sudoku.exe` or the appropriate target configuration. Windows and macOS have **not** yet been verified by this project.

Supported actions are `validate`, `solve`, `count`, `generate`, **`play`**, `--demo`, `--help`, `--version`. `generate` takes required `--seed` and `--difficulty easy|medium|hard` (no input board), optional `--symmetry none|rotational`, `--max-attempts`, `--max-checks`, `--max-nodes` and `--max-ms`. It **only emits uniquely solvable puzzles** and exits **6** with no puzzle on budget exhaustion; the CPU-time check is best-effort between node-bounded solver calls. [Generator and difficulty rubric](docs/GENERATION_AND_DIFFICULTY.md) defines algorithmic difficulty via naked/hidden singles, NOT human solving time. For `validate`, `solve` or `count`, exactly one puzzle source is required: `--puzzle DIGITS`, `--file PATH`, or `--stdin`; `--file -` means stdin. Each puzzle contains exactly **81 ASCII digits** (`0` is empty) with optional ASCII whitespace. Non-ASCII/binary bytes, conflicting clues, invalid length and inputs >1 MiB are rejected. Validating givens does *not* prove the puzzle is solvable.

`solve` prints the first deterministic valid solution and warns about multiple solutions. `count` returns exact classifications `0`, `1`, `2+` (two or more, search stops at the second). `--format text|compact|json` selects output; the JSON v1 schema and examples are defined in [docs/CLI_JSON_SCHEMA.md](docs/CLI_JSON_SCHEMA.md). `--quiet` suppresses a non-unique warning. `--output PATH` creates a **new** file only after successful processing and refuses to overwrite an existing file or symlink. It never replaces an existing destination. CLI `--output PATH` now stages and syncs the complete result before atomically publishing the new filename without overwriting an existing destination; POSIX output files are mode `0600` from creation even under a permissive umask. A crash may leave an orphaned `*.tmp.*` file; directory metadata durability after power loss and native Windows behavior are not claimed. 

Exit codes: **0** successful validation/solving/counting (including count=0), **2** incorrect invocation, **3** invalid puzzle, **4** I/O/internal error, **5** valid-but-unsolvable board requested by `solve`, **6** generator budget exhausted. Errors go to stderr and produce no JSON success output.

## Offline interactive play and saves

**Locked candidates (Pointing and Claiming):** `hint locked` or `hint locked N` (N=1–81, default 5) lists candidate eliminations where all possibilities for a digit in a 3×3 box lie on the same row/column (*pointing*), or all possibilities in a row/column lie in the same box (*claiming*). `hint apply locked [N]` explicitly removes only the corresponding **already-written pencil marks** in one undoable edit; it never places a digit, guesses from a stored solution, alters unrelated notes, or saves. Repeating the command without matching notes is a no-op that preserves Redo. An incorrect entered digit blocks these strategy recommendations. This complements `hint pairs` and `hint hidden-pairs`.

**Hidden pairs — second logical strategy:** `hint hidden-pairs [N]` previews up to N actionable hidden pairs (default 5, limit 1–81): two candidate digits that are possible in only the same two cells of a row, column or box. Unlike naked pairs, this lets you remove **other candidate marks from those two cells**. `hint apply hidden-pairs [N]` removes only matching existing pencil notes in **one undoable operation**; it never fills a digit, guesses, overwrites other notes or saves automatically. Repeating the action when no matching notes remain is history-neutral. Duplicate logical pairs discovered again in an overlapping unit are not counted twice. Wrong player entries block suggestions and application.

**Apply naked-pair pencil elimination:** `hint pairs` remains a read-only explanation, while `hint apply pairs [N]` explicitly clears existing handwritten candidates that logically cannot fit because of up to N actionable naked pairs (default 5, maximum 81). It does **not** place any digits, remove candidates from the pair's two reserved cells, or alter unrelated manual notes. All matching pencil removals form **one Undo step**; a repeat with nothing left to clear does not add a history entry or discard Redo. The existing wrong-entry guard blocks application until mistakes are corrected. This does not rewrite the Sudoku save format or auto-save.

**New naked-pair strategy:** Use `hint pairs` (up to five results) or `hint pairs N` (1–81 results) to locate two cells in the same row, column or box that share exactly two candidate digits. The output identifies which **candidate marks** those digits can be logically eliminated from in other cells of that unit. The game never chooses a hidden solution digit, applies guesses or edits your notes automatically. This is read-only strategy guidance; `hint`, `hint all`, `hint chain` and apply commands remain unchanged. The original game must not contain incorrect entries when you request it.

**New read-only focus report:** Type `focus` (default 5 cells), `focus 1`, or `focus 9` to see empty cells ranked by the **fewest locally legal candidate digits**, with ties in row-major order. The optional positive limit is 1–81. A forced single is marked; if a locally valid but wrong entry leaves an empty cell with *zero* legal candidates, `focus` explicitly displays the contradiction and warns. This is constraint guidance, **not a stored-solution lookup or a guarantee a multi-candidate guess is correct**. It does not fill values, update pencil notes, clear redo, change elapsed time or save anything.

**History navigation:** `undo [N]` and `redo [N]` now accept an optional positive decimal count (1–127, default 1). A multi-step request moves the history cursor atomically; requesting more steps than remain returns `no action to undo or redo` with the board, handwritten notes and redo branch unchanged. Invalid counts, negative numbers and extra arguments fail without edits. This is independent of the existing `hint apply chain [N]` grouping and does not change the save-file format or autosave.


To share a portable puzzle without making a save file, type `export` or `export givens` during play. The CLI prints the original 81-digit clue string in the existing `sudoku play --puzzle DIGITS` format. `export current` prints your currently entered digits instead (including possible incorrect player entries), and `export both` prints both values. These commands are **read-only** and reveal no cached solution or pencil notes; they do not preserve notes, timer, history or save destination. For a faithful session backup use `save PATH`. Only the original givens are guaranteed to remain the same uniquely solvable puzzle on import.


Start a uniquely solvable imported puzzle (`sudoku play --file tests/fixtures/unique.txt`), a generated puzzle (`sudoku play --seed 42 --difficulty easy`) or resume a saved session (`sudoku play --resume my-game.save`). Gameplay `play --file` now reads the bounded 1 MiB puzzle input from heap storage, avoiding a >1 MiB stack allocation on Windows/MSVC. Interactive `save PATH` accepts spaces in filenames (with or without surrounding double quotes); empty, unclosed, stray or nested double quotes are rejected rather than falling back to an existing save or creating an unintended filename. Once a save has replaced its destination, including with a durability warning, that path becomes the default for subsequent `save`. Type `help` for ASCII-only commands including `set ROW COL DIGIT`, `erase ROW COL`, `note ROW COL DIGIT`, `notes ROW COL`, `clear-notes`, `undo`, `redo`, `reset`, `check`, `check details`, `check clear`, `hint`, `hint all`, `hint pairs`, `hint chain`, `hint apply`, `hint apply all`, `hint apply chain`, `auto-notes`, `prune-notes`, `status`, `show`, `save [PATH]`, `quit`. Use `--save PATH` when starting a game to establish its default save destination. **Quitting never implicitly saves.** The current board and notes persist, but the previous undo/redo history intentionally resets on load. The `erase ROW COL` command also clears pencil notes from an empty editable cell; this is one undoable change, and repeating erase on an already-empty note-free cell is a no-op. A `reset` of a board with unchanged givens and no notes is now idempotent and does not insert an undo step. For packaging acceptance on a native Linux x64, Windows x64/MSVC or macOS arm64 runner, run `python scripts/platform_acceptance.py --expected ubuntu-latest|windows-latest|macos-latest` with exactly one actual runner option; a successful run requires a clean checkout (including untracked files), can enforce an explicit `--require-sha`, and writes an unsigned exact-SHA local receipt and does **not** publish a release. Save files use the checksummed `SUDOKU_SAVE_V1` format with same-directory temporary write and atomic replace. On POSIX, new save staging files are created atomically with owner-only permissions (`mkstemp`, `0600`) **from the outset**, followed by a defensive `fchmod` before writing, even with a permissive umask; native Windows file ACL validation remains pending. The save writer also rejects malformed externally edited C game states, nonunique original clues and stale cached solutions before opening a temporary file, preserving earlier valid saves. Rechecking uniqueness adds work to each explicit save. The checksum is not authentication. On POSIX v0.8.3 now also fsyncs the parent directory after a successful rename; if this last step fails, the game prints a dedicated **durability uncertainty warning**, because the target may already have been replaced. Power-loss durability is still **not guaranteed** across all filesystems, hardware or unverified Windows/macOS targets. The save format and complete terminal command contract are described in [Gameplay and save format](docs/GAMEPLAY_AND_SAVE.md).

### Manual platform evidence review (development only)

Run the **manual** GitHub Actions Sudoku quality gate on the exact development branch. Choose the default single host for a minimal run, or explicitly select `runner_os: all` to execute Linux x64, Windows x64/MSVC and macOS arm64 on the **same** commit in one opt-in dispatch. This is never triggered automatically and consumes runner minutes only when started. After `platform_acceptance.py` builds and verifies its four development archives, the runner now independently checks them with `verify_receipt_matrix.py --local` before retaining the unsigned receipt. The workflow uploads **only** `platform-receipt.json` and `SHA256SUMS` for seven days: no unlicensed development binaries or archives are published by Actions. For `runner_os: all`, an additional Linux review job retrieves those three unsigned metadata artifacts **from the same run and attempt** and automatically compares the claimed exact SHA, OS/CPU/compiler, four archive checksums and source tree digest using `--metadata-only`. The generated receipts now also record `github_run_id` and `github_run_attempt` (when running under GitHub Actions); the review explicitly requires both to match its current run and attempt, preventing accidental cross-run mixing. This is **not** physical archive verification and does not approve a release. The three native jobs independently perform full local package verification before uploading metadata. Downloaded metadata alone remains insufficient to rerun full archive inspection elsewhere. If the owner has independently obtained each runner's original four archives in private folders, verify all three together with:

```sh
python3 scripts/verify_receipt_matrix.py --require-sha "$COMMIT_SHA" \
  --linux ./evidence/linux --windows ./evidence/windows --macos ./evidence/macos
```

For a local pre-upload validation on the real runner or clean checkout, use `python scripts/verify_receipt_matrix.py --require-sha "$COMMIT_SHA" --local dist --expected ubuntu-latest` (substitute the native runner label). **All checks validate unsigned internal consistency, not publisher identity**, license approval or production readiness.

## Run quality checks

**CTest command identity preflight (v0.8.4):** Mandatory CLI checks are now bound to their exact subcommands and arguments, too: `count`/`solve`/`validate` must use the expected checked-in puzzle or 81-digit compact input, and `--help`, `--version`, and `--demo` must use their real invocations. Even a correctly built Sudoku binary running `--help` cannot stand in for a solver regression. Extra arguments and fixture substitutions fail before executing CTest.  The local `scripts/quality_gate.py` does not accept test names alone: before running CTest, it reads the actual JSON test inventory and verifies that each mandatory test executes the correct Sudoku executable **from the configured build directory**, a known C unit-test binary, or the **exact checked-in Python test script**. The CMake-based stdin test must use the real `run_stdin.cmake`, the built `sudoku` executable, and the intended `tests/fixtures/valid.txt`. A renamed `echo PASS`, unrelated script or stale system-installed executable causes a fail-closed preflight. This is registration integrity, **not proof the tests passed**; a clean native build and CTest execution are still mandatory.

The development quality gate must use **normal Python execution** with assertions enabled. Do not use `python -O`, `python -OO`, or `PYTHONOPTIMIZE` when running the CMake/CTest acceptance suite: six scriptable regression tests rely on required Python `assert` checks and now **fail closed** rather than silently skipping those validations. `scripts/quality_gate.py` validates this before starting the build, and each script also checks independently when launched directly from CTest. These guards do not replace actual native Windows/macOS acceptance, source/provenance signing, or licensing review.


For the current platform (including Windows with MSVC, provided CMake/CTest/Python and a compiler are installed):

```sh
python3 scripts/quality_gate.py --mode fast
```

Full local Linux/macOS gate with GCC/Clang/GCC AddressSanitizer/UndefinedBehaviorSanitizer, GCC line coverage threshold **90%** and deterministic CLI benchmark:

```sh
python3 scripts/quality_gate.py --mode full
```

No external Python packages are required. The output and benchmark JSON are written to `.quality-build` by default. The property test has fixed random seed `0x5EED2026`, 320 valid partially blanked boards, 128 contradictory boards, and **10,000 random parser inputs**. The generator unit test additionally checks 72 reproducible, uniquely solvable fixtures across three difficulty categories and two symmetry options. The game engine unit tests and interactive E2E script cover save/resume, malformed saves, immutable givens, undo/redo and completion. Tests also contain an independently written solution checker. Optional [libFuzzer](https://llvm.org/docs/LibFuzzer.html) harnesses in `tests/fuzz_parser.c` and `tests/fuzz_solver.c` are not included in normal builds. Execute a bounded, opt-in reproducible campaign with `python3 scripts/run_fuzz.py --runs 3000` (requires Clang/libFuzzer); the script copies the seed corpus so the repository stays clean. See [quality evidence](docs/VERIFICATION_v0.7.0.md) for explicit commands and limits.

A GitHub Actions quality gate is available through **manual `workflow_dispatch` only**. Select Ubuntu, Windows or macOS for a single native gate, or explicitly select `all` for the three native gates plus a fourth, metadata-comparison job. The default remains one Linux host, and no run is triggered by push, PR or a schedule. Running it manually consumes CI minutes. **No hosted CI run is claimed until observed.**

### v0.8.2 integrity hardening (development only)

Release verification now limits the unsigned `SHA256SUMS` input to 4 KiB before decoding, and refuses compressed TAR.GZ/ZIP archives larger than 80 MiB **before** streaming their SHA-256 digest or parsing archive entries. ZIP archive verification now preflights the canonical central directory (member count, record bounds, offset, size, and no ZIP64) before Python allocates member metadata, rejecting malformed or oversized archives. Source distribution verification now also requires an exact match between archived source files and the bundled `scripts/release_files.txt`, so dropping or adding a file cannot be hidden by recomputing an unsigned checksum manifest. Development archives also reject case-insensitive and Unicode-normalization filename/directory collisions before reading file payloads; path names are bounded to 4 KiB and 64 components. Portable archive member checks now also reject Windows device-name aliases, NTFS alternate stream colons, forbidden punctuation and trailing spaces/dots in source and installed paths. Development package construction now caps the source manifest at 256 KiB and source/install payload collections at 1,024 files / 64 MiB before reading contents into memory. Installation file paths are now enumerated incrementally, capped at 4,096 visited entries, then sorted only after bounded collection. Source-package manifests now reject symlinked parent directories and Windows-ambiguous `\\` or `:` path spellings, preventing external files from being included through directory aliases. The TAR verifier also streams member metadata under a strict 1,024-file limit rather than preloading an unbounded member list. Cross-platform evidence now compares canonical source-file contents via schema-v2 receipts; it does not require independently compressed ZIP/TAR bytes to be identical across different hosts. Per-platform archive SHA-256 checks remain mandatory, and all evidence remains unsigned and non-release-grade. The native development package verifier now checks archive content consistency **across both ZIP and TAR.GZ**, not just their SHA-256 manifest, and rejects symlink, traversal, duplicate and oversized archive records. Run `ctest` on an uninstrumented Release build to execute the adversarial packaging tests; see [v0.8.2 evidence](docs/VERIFICATION_v0.8.2.md). These checks do not authenticate the publisher or substitute for Windows/macOS validation and an owner-approved license.


**v0.8.4 receipt verifier detail:** Both `--local` and the three-platform matrix validate all four actual ZIP/TAR.GZ archives, not only receipt hash strings: the existing package verifier enforces regular files, canonical paths, binary ZIP/TAR content equality, required executable/header files and source archive membership. These are offline structural checks of unsigned files, not origin authentication. The manual workflow retains only the metadata files; a later full archive matrix still needs copies of the original archives from each host.


**v0.8.4 canonical archive modes:** The development package verifier checks ZIP/TAR file permissions as well as their contents. Source files and non-executable installed assets require `0644`, while installed `bin/` files require `0755` on all platforms, so a Linux/macOS binary cannot silently lose its executable bit and still pass verification. These are archive metadata checks, not proof that the binary runs on supported native hosts.
