# v0.7.0 interactive terminal gameplay and save contract

Sudoku `play` is a local, plain-text terminal interface. It never makes network requests, requires no ANSI color, and can read scripted commands from stdin. A playable puzzle must have **exactly one solution**; invalid, unsatisfiable and non-unique puzzles are rejected before the session starts.

## Start a game

```sh
./build/sudoku play --file tests/fixtures/unique.txt
./build/sudoku play --puzzle 034678912672195348198342567859761423426853791713924856961537284287419635345286179
./build/sudoku play --seed 42 --difficulty easy --symmetry rotational --save my-game.save
./build/sudoku play --resume my-game.save
./build/sudoku play --help
```

The `--file` argument reads a puzzle file (max 1 MiB), not a saved game. On POSIX, both `play --file` and the `validate`/`solve`/`count --file` commands now open nonblockingly and check the actual opened descriptor is a regular file: a writer-less FIFO or character device is rejected promptly; symlinks to ordinary regular puzzle files remain supported. Solver commands still support `--stdin` and `--file -` for streamed input; interactive play reserves stdin for commands. On POSIX, `--resume` accepts only regular saved files (including ordinary symlinks to regular files): it opens the path nonblocking and rejects named pipes or character devices before reading, avoiding a terminal session hanging on an accidental FIFO path. The loader returns a file-operation error without changing an existing game. Windows retains the previous standard-file loader until native acceptance. `--resume` reads only versioned Sudoku game saves. For an interactive game, puzzle input through stdin is not supported because stdin is reserved for player commands. A generated game requires both `--seed` and `--difficulty`; `--symmetry` applies only to generated games. There is no network dependency.

## Interactive commands

Input is handled as a byte-counted line until newline or EOF. An embedded NUL
byte causes the **entire** command to be rejected instead of silently executing
the prefix before NUL (notably a dangerous partial `save PATH`). Other ASCII
control bytes (such as ESC, Backspace, DEL and form feed) are rejected before
a path can be created or echoed to the terminal. Tabs remain valid command
separators. One terminal CR immediately preceding newline or EOF is accepted
for Windows-style line endings; an embedded CR is rejected to prevent terminal
line rewriting. Commands longer than the fixed input buffer are likewise
drained and rejected; the next complete command is processed normally.
The last line remains valid without a trailing newline. Input read errors
return exit code 4. This prevents malformed scripted input from being
interpreted as different gameplay actions or producing terminal control
sequences.

| Command | Behavior |
|---|---|
| `show` | Print the complete board and progress. Zero cells appear as `.`. |
| `export` / `export givens` | Print the original **81-digit** puzzle as `Puzzle givens: DIGITS`, suitable for a new `sudoku play --puzzle DIGITS` session. Read-only and independent of the player's edits. |
| `export current` | Print the current player's board as `Current board: DIGITS`. This can include wrong user-entered digits and may therefore fail to import as a solvable puzzle. Does not expose unentered correct answers. |
| `export both` | Print the original clues and current board on two separate lines without touching saves or history. |
| `set ROW COL DIGIT` | Fill an editable cell, coordinates and digit 1–9. Sudoku rule conflicts are rejected. |
| `erase ROW COL` | Clear the placed digit **and all pencil notes** from an editable cell. Erasing a blank cell with notes is undoable; repeating erase on a blank note-free cell is a no-op. |
| `erase batch r1c3,r1c4` | Clear a comma-separated list of 1–81 distinct editable cells, **including digit and notes**, as one Undo action. Strict lowercase `rNcM` coordinates, no spaces within the list. All targets are validated before commit: a clue, duplicate, invalid coordinate or corrupted live state rejects the whole batch without changing any cell or Redo. A batch whose cells were already blank and note-free is a no-op and preserves Redo. No solution lookup or implicit save. |
| `erase row N` / `erase column N` / `erase box N` | Clear **only editable cells** in the selected 1–9 row, column or 3×3 box (boxes numbered row-major). All entered digits and pencil marks in that unit are cleared atomically via `sudoku_game_erase_many`, with a single Undo step if anything changes. Givens remain untouched. A fully unchanged unit preserves Redo; malformed unit/scope or invalid live state is rejected without edits. Never automatically saves or reads solution digits. |
| `note ROW COL DIGIT` | Toggle a pencil note 1–9 on an empty editable cell. |
| `notes ROW COL` | List the pencil notes for one cell. |
| `notes batch r1c3=19,r1c4=-` | Replace pencil marks on up to 81 distinct editable empty cells atomically in one Undo action. `rNcM=DIGITS` uses distinct ASCII digits 1–9; `rNcM=-` clears a cell's marks. Items are comma-separated without spaces. Any invalid mask, duplicate, filled/given cell or malformed live state rejects the complete batch and preserves Redo. Identical masks make a no-op. Does not change board digits, reveal the solution or save implicitly. |
| `notes batch add r1c3=2,r1c4=4` / `notes batch remove r1c3=1,r1c4=6` | Atomically **add or remove** selected handwritten marks in up to 81 distinct editable empty cells. Unlike `notes batch` replacement, existing marks not mentioned remain unchanged. Each successful non-no-op operation creates one Undo snapshot; repeated additions or absent-mark removals preserve Redo. Invalid masks, duplicate positions, givens, filled cells or corrupt state abort the entire batch. Strict comma-separated syntax and no implicit save. |
| `notes batch toggle r1c3=12,r1c4=24` | Flip each selected handwritten mark in up to 81 distinct editable empty cells as one Undoable transaction. Specified marks already present are removed, absent marks are added; other notes and board digits remain unchanged. Strict `rNcM=DIGITS` syntax, atomic duplicate/given/filled/mask validation. A `-` mask (zero bits) is a no-op, preserving Redo. This never uses the cached solution or saves automatically. |
| `notes batch preview r1c3=19,r1c4=-` / `notes batch preview add\|remove\|toggle r1c3=2,r1c4=4` | **Read-only transaction preview:** validate an entire explicit list using the same C11 engine on a private game copy, then report the number of cells whose marks would change and each changed mask (`old -> new`, `-` for none). The four modes are set (default), add, remove and toggle. Malformed/duplicate/given/occupied targets fail without modifying the player's board, Undo/Redo history, clock, or save. A zero-change preview retains any pending Redo. The preview never consults the solution. |
| `candidates ROW COL` | Show digits currently legal under Sudoku row/column/box rules in an **empty** cell, without consulting the hidden solution or changing notes/history. A filled cell reports its current digit. |
| `focus [N]` | Rank the N most constrained **empty cells** by how many row/column/box candidates remain (optional decimal N=1–81, default 5). Ties use row-major order, and every printed cell includes its locally legal digit list. Zero-candidate cells are listed first and trigger a contradiction warning. One-candidate cells are labelled forced singles. **Read-only**, no stored-solution lookup and no guarantee that a two-or-more-candidate guess is correct. Invalid N or arguments do nothing. |
| `hint` | Preview the first naked or hidden single without changing the board, notes, save destination or undo/redo. Refuses to suggest a potentially misleading step while incorrect entries remain. Takes no arguments. |
| `hint all` | List **all distinct cells** with an immediately forced naked or hidden single. Read-only: never inserts digits, reads the stored solution for hints, edits notes or creates undo history. Lists naked singles before hidden singles and never repeats a cell forced by multiple units. Blocked when incorrect player entries remain. |
| `hint pairs [N]` | Show up to N **actionable naked pairs** (optional N=1–81; default 5). Two empty cells within the same row, column or box have exactly the same two legal candidates, so those digits can be eliminated as candidates from every *other* cell in that unit. Lists the pair and exact eliminations in row → column → box order. A pair without any elimination is omitted; three matching cells are not mistaken for a pair. Read-only: the game does not actually erase pencil marks, place digits, change history or consult the stored solution. Refuses to suggest potentially misleading deductions while incorrect entries remain. |
| `hint hidden-pairs [N]` | Preview up to N actionable **hidden pairs** (optional N=1–81, default 5): two digits that each appear as a candidate in exactly the same two empty cells of a row, column or box. Other candidates **inside those two cells** can therefore be eliminated. Print coordinates, reserved digits and removable extra candidates. An identical pair found in overlapping units is printed only once. Preview does not modify board, notes, history, timer or save. |
| `hint locked [N]` | Preview up to N **locked-candidate** deductions (optional N=1–81, default 5). *Pointing:* if all the candidates for digit D in a box occupy one row or column, eliminate D from that line **outside the box**. *Claiming:* if all candidates for D in a row or column lie in one box, eliminate D from the box **outside the line**. Reports source cells and precise target cells; scans pointing before claiming in deterministic box/row/column order. Requires at least two source cells and at least one actual candidate to eliminate. Read-only and never uses the cached solution to choose deductions. |
| `hint apply locked [N]` | Apply up to N of the same pointing/claiming deductions to **existing handwritten pencil marks** only. Collects eliminations across all chosen patterns into a single Undo transaction, or remains history-neutral if no matching notes exist. Does not fill numbers, guess, clear unrelated notes or save. Rejects known incorrect player entries and malformed limits. |
| `hint apply hidden-pairs [N]` | Apply the union of those hidden-pair eliminations to **existing handwritten pencil notes** in the selected pair cells. All requested removals form one transactional Undo entry; no matching notes means no history entry and preserves Redo. Never changes cell digits, reveals the solution or erases unrelated notes. Blocks incorrect entries, and strictly rejects invalid counts/extra arguments. |
| `hint apply pairs [N]` | Explicitly apply the logical eliminations from up to N actionable naked pairs (optional N=1–81; default 5) to the **player's existing pencil notes only**. The two pair cells are never cleared by their own pair. Every selected removal is validated and combined into one undoable history snapshot, even across different rows/columns/boxes. If the selected pairs have no matching handwritten marks, no history state is added and redo remains intact. Incorrect player digits block application. Never places digits, guesses or saves automatically. |
| `hint apply` | Explicitly place **one** such logical single through the normal, undoable move API. Does not act if the game has incorrect player entries, no simple hint exists or the game is solved. No implicit save. |
| `hint apply all` | Commit every currently forced distinct cell as **one transactional, undoable action**, so one `undo` reverts all newly placed digits. Batch validation rejects conflicting, duplicate, out-of-range or immutable-cell placements before committing any change. If incorrect entries remain or no simple hint is available, nothing changes. No implicit save. |
| `hint chain [N]` | Preview at most **N successive** naked/hidden singles (optional N=1–81, default 81). Each step is computed against a private simulated game containing the previous step; actual game, notes, save and history stay unchanged. Prints numbered steps; stops if deductions run out and never guesses. |
| `hint apply chain [N]` | Apply at most **N** successive forced singles (optional N=1–81, default 81) as **one** transaction with one Undo entry, even when later deductions depend on earlier cells. All proposed placements are validated before committing. Refuses existing incorrect entries; stops when singles are exhausted, so a hard puzzle may remain incomplete. |
| `auto-notes` | Replace pencil marks on every empty editable cell with all currently legal candidate digits, using one undoable action. Does not place digits, change givens or reveal the stored solution; repeating it without board changes is a no-op. Takes no arguments. |
| `prune-notes` | Remove only pencil marks now ruled out by the live grid; preserve legal manual marks without auto-adding missing candidates. One undoable operation if notes change, otherwise a no-op. Takes no arguments. |
| `clear-notes` | Remove all pencil notes from the whole board as **one undoable action**, retaining every placed digit. If no notes remain, no history entry is created. Takes no arguments. |
| `undo [N]`, `redo [N]` | Revert or replay **N previous actions** (optional N=1–127, default 1), including placements, erasures, note edits and reset. The whole request is atomic: if insufficient steps remain, none are applied. New edits discard the redo branch. Invalid counts or surplus arguments leave the state untouched. |
| `reset` | Restore original givens and clear notes. Can be undone while history remains. |
| `check` | Count empty and incorrect cells without printing the answer. |
| `check details` | List each incorrect player's row, column and currently placed digit, **never** the correct solution digit. Read-only, with no state or history edits. Empty/correct boards report no incorrect entries. |
| `check clear` | Explicitly erase **all** currently incorrect player-entered digits as **one undoable action**, without filling in correct digits. Correct placements, original givens, and notes in unrelated cells remain intact. Repeating without mistakes does not change history or discard redo. No arguments. |
| `history summary` | Read-only totals for the **retained** snapshot timeline: applied versus redoable action counts, placed/erased/replaced digits, pencil marks added/removed and per-step touched cells. Bulk edits count once as an action but include each affected cell. Repeated edits are counted as transitions, not net current-board changes; older edits dropped by the 127-step history limit are excluded. Never reveals the solution, edits the board or moves the Undo cursor. | 
| `history hotspots [N]` | Read-only ranking of the N most frequently changed cells in the retained 127-action Undo/Redo history (1–81, default 10). Shows how many snapshots changed each cell's digit or notes, with separate digit, note, DONE and REDO counts. A simultaneous digit-and-note change is **one edited step**, but contributes to both detail counts. Ties resolve in row-major order. Excludes evicted history, never reveals the stored solution, and does not change the game, cursor, timer or save. |
| `history heatmap [all\|done\|redo]` | Render a **9×9 read-only numeric map** of per-cell edit frequency across retained Undo/Redo snapshots (default `all`). `done` counts applied transitions; `redo` counts redoable transitions; `all` counts both. A simultaneous digit-and-pencil change counts as one edited step. Includes per-scope totals, excludes evicted history, never exposes the stored solution or modifies the board, cursor, timer or saves. |
| `status` | Filled cells, incorrect entries, time spent, available undo and redo steps. |
| `save [PATH]` | Persist state to a supplied path or the previous `--save`/`--resume` path. The rest of the command line is interpreted as a filename, so spaces work; optional surrounding double quotes are removed. Empty quoted filenames, unmatched opening quotes, and any stray or nested `"` characters are rejected without creating or overwriting save files. Literal double quotes in save filenames are unsupported. |
| `quit` / `exit` | Leave without an implicit save. |
| `help` | Show the interactive command summary. |

The new `hint chain [N]` command simulates up to N forced single placements (1–81 inclusive, default 81) on a private copy of the game and prints each deduced cell in deterministic order. A newly placed digit can reveal another naked or hidden single that was not present in `hint all`'s immediate snapshot. `hint apply chain [N]` commits up to N successive deductions through the transactional multi-move API in one Undo action, never one history edit per step. The simulation and the real board do not read stored solution digits to *choose* placements; the existing wrong-entry guard uses the verified solution only to prevent misleading hints. A chain stops rather than guessing when no single remains, and preview is read-only; no automatic save is performed. For example, the 30-clue fixture provides 16 immediate forced cells but a 51-step chain that fills the entire board, while a 25-clue fixture stops after 8 chain steps without solving the puzzle.

The new `hint pairs [N]` reports **naked-pair candidate eliminations** rather than filling digits. It considers units in row, column and box order, and only reports a useful pair if two (not three) empty cells share exactly the same two locally legal candidates *and* some other cell in that unit currently allows one of those digits. Its `r5c2(3,7)` notation means *eliminate candidate marks 3 and 7 from row 5, column 2*, not fill the cell. The command is educational and read-only: it does not remove pencil notes, create an Undo entry or change the saved game. As with `hint`, wrong entered digits block recommendations, and no solution cache is used to generate eliminations. `hint pairs 1` limits output to one pair; `hint pairs` defaults to five reports. If no actionable pair is found, the game says so rather than inventing a hint.

The game uses 1-based row/column coordinates. The givens are immutable. `hint` offers a limited logical deduction rather than looking up the stored solution: it searches single-candidate cells in row-major order, then scans row, column and box constraints for a single place to put a digit. It prints the chosen row/column, digit and reason, but does not insert that digit or edit any pencil marks. Use `hint all` to enumerate every immediately deducible cell using the same candidate and unit constraints, listing naked singles first and then hidden singles in deterministic row/column/box scan order. A cell is printed once even if multiple units force it, and listing never edits the game, pencil notes or Undo/Redo state. Use `hint apply` to place the first offered deduction as one undoable move, or `hint apply all` to place all currently available distinct deductions in one transactional history snapshot. The bulk operation validates every proposed placement and the resulting grid before changing any live state; a failed batch preserves the prior board, pencil notes and redo branch. As with other automatic hints, incorrect player entries block this action. Both hint preview and hint apply check the current game's known mistake count against its verified solution and refuse to suggest a potentially misleading move until incorrect entries are fixed; only the explicit apply mode mutates the board. It never auto-saves, and a single invocation never fills multiple cells. If no simple deduction is available, it reports this honestly rather than guessing; a fully completed board reports that no hint is needed. A wrong but locally nonconflicting entry can make a deduction misleading; both hint commands therefore refuse to proceed until all known incorrect entries are cleared. Use `check details` to locate the offending rows and columns without exposing answer digits. This verification relies on the internally verified unique solution only to identify wrong placements, not to compute or disclose hint digits. Invalid `hint` arguments other than the single literals `all` and `apply` are rejected without altering game state. `candidates` calculates currently legal values from the **live board**, not the puzzle's verified solution; therefore it cannot spoil the answer and can list multiple options. Its output is read-only and does not depend on pencil notes, create an undo state, clear redo or modify a save. For example, with the standard sample puzzle, `candidates 1 3` prints `Candidates for row 1 col 3: 1 2 4`; `candidates 1 1` reports that the original clue is already filled. Invalid coordinates, a third argument or a missing coordinate are rejected. Pencil notes are intentionally independent of the authoritative engine candidates: they are personal annotations, not automatic hints. Manual `note` continues to toggle any 1–9 pencil mark; `auto-notes` is an explicitly requested bulk replacement of those personal marks with legal row/column/box candidates for the *current* filled grid. It uses the shared `sudoku_game_candidates` engine function, not the stored solved grid, and writes one history snapshot only when at least one note changes. A subsequent `undo` restores the player's previous manual notes, `redo` restores the generated notes, and `save` persists the generated masks in the existing version-1 save format. Auto-notes does not automatically recalculate after every future move: run it again to refresh candidates. The candidate helper has the same rule semantics as before, but checks board validity once and then calculates unavailable digits from the cell's row, column and box; a malformed or conflicting board still returns no candidates. Alternatively, run `prune-notes` after filling cells to discard **only** newly illegal pencil marks, preserving the player's selected subset of still-legal candidates. Pruning is an explicit one-step undoable edit when it changes anything; repeating it unchanged is history-neutral. Neither command consults the stored completed solution. Both commands validate the current board first and reject conflicting or out-of-range public board values without changing notes or undo history, preventing an invalid board from silently wiping annotations. Valid bulk operations reuse a prevalidated candidate-mask helper, avoiding an additional full-board check for every empty cell. The player may enter an incorrect digit as long as it does not directly violate row, column or box constraints; `check` compares it with the **verified unique solution**. After inspecting errors with `check details`, the player can choose `check clear` to erase all incorrect entries with one reversible history snapshot. This command uses the internal solution to distinguish correct from incorrect values, **but never prints or inserts an answer**. On an invalid game structure exposed by the public C API, it refuses to alter any state; clearing an already error-free board is a true no-op. A successful correction prints how many incorrect entries were erased (or reports that none needed clearing). Completion is detected only when the board matches all 81 digits of that solution, not merely when all cells are nonempty.

Erasing an editable cell now clears **both** any placed digit and its note mask. This fixes the former no-op behavior when an empty cell still contained pencil marks, without adding a second command: `undo` restores the erased notes, `redo` clears them again, and no history step is created if there was nothing to erase. Given cells remain immutable.

Undo/redo in memory is bounded to the most recent **127 state transitions** (128 snapshots, one base state). Each snapshot contains board and notes; reset is a single undoable step **only when the board or notes actually change**. Repeating reset on an already-cleared board creates no new undo/redo history. A freshly loaded game resumes the current board and notes with a **new undo history**; previous history is intentionally not serialized. Timer tracks active session wall-clock seconds and persists elapsed seconds on save. Time while the program is closed does **not** count; clock changes may affect elapsed seconds.

## Save file format: `SUDOKU_SAVE_V1`

A strictly parsed UTF-8-compatible **ASCII** document (maximum 1,024 bytes), with exactly these six lines and a final LF:

```text
SUDOKU_SAVE_V1
G=<exactly 81 ASCII digits, original givens>
B=<exactly 81 ASCII digits, current board>
N=<exactly 243 uppercase hex digits, 3 hex digits per 9-bit note mask>
E=<canonical decimal elapsed seconds, 0..315360000; no leading zeroes except exactly 0>
C=<16 uppercase hexadecimal digits: FNV-1a 64 of all bytes preceding the C line>
```

Each note mask uses only digit bits 1–9 (`0x000`–`0x3FE`); bit zero must be clear. Original clues and filled cells must not have notes. The current board must be Sudoku-rule-consistent and must preserve all givens. The original puzzle must have a unique exact solution. **The checksum detects accidental truncation or corruption; it is not cryptographic authentication** and does not defend against deliberate malicious modification. The parser rejects any extra or missing byte, invalid checksum, illegal note bit, contradictory number or altered original clue. It also rejects noncanonical elapsed-time decimal encodings such as `E=00` or `E=0012`, **even with an otherwise valid checksum**. The elapsed-time getter clamps unexpected out-of-range public structure values to the documented 315360000-second bound. Failed loading leaves any caller-owned game unchanged. There is no compatibility promise for unknown future save versions.

### Atomic save strategy

1. Before rendering, validate the caller-owned `SudokuGame` state: both boards must obey Sudoku rules; the original givens must **still have exactly one solution** matching the cached solved board; all givens must remain unchanged; no filled cell may retain notes; and note masks must be legal. This repeat-solve verification occurs on explicit save, including for consumers that mutate the public C struct directly. This guards clients of the public C API that modify the exposed struct without using safe mutators. Invalid state is rejected *without creating any temporary file or replacing an earlier valid save*. Then render the canonical, checksummed record in memory.
2. Create a fresh, exclusive temporary file **in the same directory** as the destination. POSIX now uses `mkstemp` with a same-directory `.tmp.XXXXXX` suffix, creating an exclusive owner-only (0600) stage without a process-global serial, followed by `fdopen`, which makes the temporary file private **from birth**, including with a permissive `umask(000)`; a defensive `fchmod(0600)` also runs before writing any save bytes. Windows uses exclusive `fopen(..., "wbx")` with an atomic per-process `InterlockedIncrement` serial and process ID in the staging name; native Windows validation is still required. Failed `fchmod` or `fdopen` aborts and cleans up without replacing the old target. An atomic rename installs the new file's permissions, so the POSIX replacement remains private.
3. Write the entire record, `fflush`, `fsync` (POSIX) or `_commit` (Windows), then verify `fclose` succeeded.
4. Replace the target with same-filesystem `rename` (POSIX) or `MoveFileExA` with replacement/write-through (Windows). If file write, file sync or rename fails, the temporary file is deleted and the previous target remains unchanged.
5. **POSIX only:** open the containing directory **nonblocking**, request a directory-only descriptor where supported (`O_DIRECTORY`), verify the opened descriptor is actually a directory (`fstat`), then call `fsync` and check `close`. If the directory pathname has been replaced with a FIFO after `rename`, return a **durability-uncertain** warning without hanging; the target replacement has already completed and cannot be treated as a failed rename. This is best-effort metadata persistence, not a guarantee against power loss.

If directory `fsync` fails **after a successful rename**, the game returns a distinct `SUDOKU_GAME_DURABILITY_UNCERTAIN` status. In v0.8.4 the terminal also retains an explicitly supplied save destination as the default for a later bare `save`, because the rename already succeeded. The terminal prints a warning that the **target was already replaced but survival of sudden power loss cannot be promised**; this is not a pre-rename failure and does not claim the previous file survived. The newly written save can normally be loaded immediately; this still does not establish durability after a hardware failure.

An unexpected crash before rename can leave an orphaned temporary file; the old save remains intact, provided the filesystem honors same-directory rename semantics. A power loss at any phase, especially on a filesystem without reliable `fsync`/write barriers, may lose the latest version, so **durability is not formally guaranteed**. Windows uses `_commit` and `MoveFileExA(...WRITE_THROUGH)` but has not been verified on a native Windows runner. POSIX directory `fsync` is a best-effort metadata durability step, not a portable hardware guarantee. This is distinct from the other CLI commands' exclusive-create `--output`, which intentionally refuses overwrite. Do not manually rename a `.tmp.*` file to `.save`; recover from an earlier verified save instead. Tests simulate an orphan and verify that it cannot silently replace the verified save.

**Security scope:** Local paths are user-selected, so only save to trusted directories. Game files are not authenticated or encrypted. Save file corruption must never crash the program or cause a partially validated state to be accepted; test cases exercise wrong checksum, truncated file, and oversized input.

## Exit codes and limitations

`0` successful session/quit; `2` incorrect CLI options; `3` invalid/non-unique/unsatisfiable puzzle or corrupt save; `4` I/O failure; `6` generator budget exhaustion. Errors while using an interactive command are shown in-session, allowing correction and continuation. **Interactive save errors do not terminate the running game**; always confirm a successful `Saved to ...` message before quitting. The program is intentionally non-graphical, not a full-screen TUI.

Windows/macOS native builds and atomic replace behavior have **not** been tested yet. The manual CI workflow is available but no hosted run is claimed. Cross-platform release verification remains required for v0.8.0.


### v0.8.4 — POSIX concurrent staging filenames

The previous game save writer derived the temporary filename from `time(NULL)` and a mutable `static unsigned serial`. That made names predictable and introduced a data race if multiple threads invoked the public API concurrently. On POSIX, `sudoku_game_save` now uses `mkstemp("...tmp.XXXXXX")` to atomically create an exclusive, unpredictable, owner-only staging inode alongside the destination. The existing defensive `fchmod(0600)`, file `fflush/fsync`, same-directory `rename` and containing-directory `fsync` remain unchanged. A stage-creation failure returns `SUDOKU_GAME_IO` without replacing an earlier save. The Windows `fopen("wbx")` branch has now also been hardened with an atomic `InterlockedIncrement` counter and process ID in staging names; its native multi-thread behavior remains unverified until the Windows CTest gate executes.

The Linux `tests/fault_inject.c` interposer now supports `SUDOKU_TEST_FAULT=stage-create`; `tests/save_faults.py` checks that the previous save survives the injected failure and that no temporary file remains. This full fault-injection CTest still requires an actual Sudoku binary and has not been run in this cycle.


### v0.8.4 — Windows concurrent save staging

The Windows implementation retains exclusive `fopen("wbx")` creation and atomic `MoveFileExA` replacement, but replaces the shared non-atomic `static unsigned serial` with a `volatile LONG` incremented using Win32 `InterlockedIncrement`. Staging paths include `time(NULL)`, `GetCurrentProcessId()`, and the incremented serial. These changes reduce process and thread collisions without modifying the v1 save-file format, overwrite contract or failure cleanup. The exclusive-open `x` mode is still the final collision guard. They do **not** establish Windows file-ACL equivalence with POSIX 0600 or durable power-loss semantics.

A native Windows-only CTest (`sudoku_windows_save_concurrency`) starts 12 threads that concurrently attempt eight writes each to one solved game destination. Some transient `SUDOKU_GAME_IO` outcomes during competing replacement attempts are allowed; the suite must observe at least one successful save, zero unexpected result codes, a final valid solved game on reload and no leftover `*.tmp.*` staging files. It runs only on Windows, not in Linux CTest. Native Windows/MSVC execution is **still pending**.
